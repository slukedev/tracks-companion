# ADR-0005: Legacy Subsonic auth only through per-client app passwords

**Status:** Accepted
**Date:** 2026-11-14
**Deciders:** Tracks maintainer

## Context

Subsonic token auth sends `t = md5(password + salt)`. To verify it, the server must know the
password in plaintext. Navidrome stores login passwords reversibly under a default key found in
its source; gonic stores them in plaintext. OpenSubsonic adds `apiKey` and recommends dropping
token auth, but many clients only support the old way.

## Decision

- Login passwords are Argon2id hashes and are never accepted by `/rest`.
- `apiKey` is always accepted.
- For old clients, a user (if allowed) creates an **app password** per client in the dashboard.
  It is random, generated by the server, scoped (default library, stream, write), revocable,
  shows last use, and is stored as a SHA-256 hash plus a copy sealed with XChaCha20-Poly1305
  under a key derived from `<data>/secret.key`, which lives outside the database.
- `u`+`t`+`s` and `u`+`p` are checked against the user's active app passwords.
- Legacy auth is per-user opt-in and can be turned off server-wide.

## Options Considered

### Option A: Reversible login passwords (Navidrome)
| Dimension | Assessment |
|---|---|
| Complexity | Low |
| Cost | Login passwords recoverable from a stolen database |
| Scalability | n/a |
| Team familiarity | n/a |

**Pros:** Works with every client using the normal password.
**Cons:** Weakest storage; exposes the account password, often reused elsewhere.

### Option B: apiKey only
| Dimension | Assessment |
|---|---|
| Complexity | Low |
| Cost | Breaks many clients |
| Scalability | n/a |
| Team familiarity | n/a |

**Pros:** Cleanest.
**Cons:** Excludes clients without OpenSubsonic support.

### Option C: Per-client app passwords (Ampache's model, chosen)
| Dimension | Assessment |
|---|---|
| Complexity | Medium |
| Cost | One more key type |
| Scalability | n/a |
| Team familiarity | Medium |

**Pros:** Login password never exposed; each client revocable; damage limited by scope.
**Cons:** Anyone with the database and `secret.key` recovers app passwords; MD5 tokens over plain
HTTP can be replayed.

## Trade-off Analysis

Option C keeps compatibility while confining the weakness of MD5 auth to random, scoped,
revocable secrets.

## Consequences

- Easier: compatibility with old clients without endangering accounts.
- Harder: users of old clients take one extra step (create an app password).
- Revisit: remove legacy auth in a future major if the ecosystem has moved to `apiKey`.
